# WolfOrder — حزمة التعديلات الكاملة

تحتوي النسخة على التعديلات الـ12 وإصلاح مشكلة الصورة. بُنيت على الأرشيف المرفوع والمراحل السابقة. أي تعديل محلي آخر لم يُرسل يحتاج مقارنته قبل استبدال ملفه.

## التركيب بالترتيب

1. احتفظ بنسخة من مشروعك الحالي. أبقِ ملف `.env` ومتغيرات السيرفر الحالية، خصوصاً `JWT_SECRET`، حتى تبقى الجلسات الحالية صالحة.
2. **قبل تشغيل الكود الجديد**، افتح Supabase → SQL Editor وشغّل هذا الملف فقط:

   `database/2026-11-13-all-requested-updates.sql`

   يجمع تجهيز الصور وجدول محاولات الدخول ودواله. يمكن تكراره ويحافظ على الصور الحالية؛ لا يحذف أو يعدّل جماعياً الطلبات أو الأصناف أو المخزون أو الحسابات. إذا طبّقت SQL الصور سابقاً، يبقى هذا الملف مناسباً. لا تشغّل الملفين المنفصلين بعده. تسجيل الدخول الجديد يحتاج نجاح هذا SQL.

3. في Storage تأكد أن bucket باسم `instagram-storefront-images` موجود، و**Public bucket معطّل**، وحد الملف **3 MiB = 3145728 بايت**، والأنواع المسموحة `image/jpeg` و`image/png` و`image/webp`. لا تضف `application/octet-stream` إلى التخزين؛ السيرفر يحدد النوع من محتوى الملف. الزبون يشاهد الصورة عبر التطبيق وروابط موقّعة.
4. انسخ ملفات مجلد `wolforder` إلى مشروعك، مع إبقاء إعدادات بيئتك. الحزمة لا تحتوي `.env` أو `node_modules` أو سجل Git. نفّذ `npm ci` وأعد تشغيل السيرفر بالطريقة المعتادة؛ `npm start` للتشغيل المباشر. يمكن استخدام `npm ci --omit=dev` في الإنتاج دون أدوات الاختبار.
5. حدّث الصفحات المفتوحة لتحميل النسخة الجديدة. تم تحديث أرقام نسخ الملفات وذاكرة التطبيق. تبقى روابط المتاجر وصورها السابقة كما هي.

هذه تعليمات تحديث المشروع العامل الحالي، وليست تهيئة قاعدة جديدة. ملفات سبتمبر القديمة باقية للمرجع؛ لا تُعد تشغيلها فوق قاعدة محدثة لأنها قد تستبدل دوال حالية. هذا الدليل هو الأحدث.

صورة المتجر تُحفظ بجودتها الأصلية دون ضغط أو تصغير إضافي، وتظهر في مربع 100×100px. حد الواجهة والسيرفر أصبح 3 MiB. فحص JPG يقبل البيانات الإضافية بعد نهاية الصورة، مثل ذيل Samsung في الملف المرفوض، ويتعامل مع MIME الرفع `application/octet-stream`.

الأصناف المؤرشفة السابقة تبقى في القاعدة وتظهر متوقفة بالمحرر. عند حفظ الصنف تُثبت الحالة المختارة فعال/متوقف؛ لا يوجد تحويل جماعي للحالات. حسابات المخزون والمبيعات ودوال حفظها بقيت كما هي.

الرئيسية المحسّنة هي صفحة شركة إنستغرام ذات البطاقتين، وليست لوحة الشركة الأساسية لإضافة طلبات التوصيل. العرض الافتراضي للمدير الأساسي يبقى طلبات اليوم وقيد المتابعة والمعدّلة اليوم؛ اختر تواريخ محددة لعرض التاريخ المطلوب.

كلمات المرور وأسماء الدخول والمعرّفات لا تُحوَّل عند توحيد الأرقام. كلمات المرور القديمة لا تُعرض؛ التغيير يستخدم bcrypt ويتحقق من صلاحية المدير على السيرفر، ويحدّث كلمة المرور وحدها دون تغيير الدور أو إنهاء الجلسات الحالية.

قفل الدخول يعمل بالمسار المشترك للحسابات، بما فيها مشاهدة إنستغرام الخاصة بالشركة. الطلبات أثناء الحظر لا تمدد المهلة، والحسابات الأخرى والجلسات الحالية تبقى فعالة. القفل العام بعد ثلاث محاولات يتيح لمن يعرف اسم الحساب إحداث قفل مؤقت؛ منعه بالكامل يتطلب تغيير السياسة أو تحققاً إضافياً خارج النطاق المطلوب.

## التحقق

بعد `npm ci`:

```bash
npm test
npm run test:inventory
```

تستخدم اختبارات قاعدة البيانات PostgreSQL مضمّناً وبيانات مصطنعة؛ لا تتصل بقاعدة Supabase الفعلية. تشمل الصلاحيات وكلمات المرور والقفل المتزامن وانتهاءه وبقاء الجلسات، والصور وعزل الشركات، وفلتر الجرد والأرقام ومفتاح الصنف والتحديد الجماعي والبحث ومعاملات الطلبات والمخزون والتصدير. نجحت 114 حالة في مجموعة المشروع و34 حالة مستقلة لدوال المخزون والترحيل، على Node.js 24.22.1. أُجري أيضاً فحص صياغة JavaScript ومراجع الملفات المحلية.

تعذّر فتح المعاينة المحلية في متصفح بيئة العمل؛ لذلك لم يُتحقق بصرياً من العرض الفعلي على الموبايل والكمبيوتر. اختبارات DOM لا تحل محل هذا الفحص. بعد التركيب راجع:

- رفع JPG بين 2 و3 MiB واستبداله وحذفه، مع بقاء صورة المتجر الآخر ورابطه.
- رابط الزبون والشعار والترويسة ومربع الصورة وإرسال طلب تجريبي.
- الرئيسية والجرد والأصناف ونافذة تعديل الطلب في الوضعين، وعرض 320px و375px والكمبيوتر.
- كل تفاصيل بطاقة الطلب الـ18 وإجراءاتها وتحديد الكل، مع بقاء جدول الكمبيوتر.
- اختيار صنف واحد ثم جميع الأصناف ومقارنة أرقام الجرد والمبيعات.
- تغيير كلمة مرور حساب تجريبي من المدير، ورفض المسار للشركة والسائق.
- ثلاث محاولات خاطئة لحساب تجريبي، ثم إعادة فتح الصفحة واستمرار الحظر، ودخول حساب آخر، ثم المحاولة بعد انتهاء الخمس دقائق.

لم يُنفذ SQL على قاعدة الإنتاج، ولم تُرفع الملفات إلى GitHub أو السيرفر.
